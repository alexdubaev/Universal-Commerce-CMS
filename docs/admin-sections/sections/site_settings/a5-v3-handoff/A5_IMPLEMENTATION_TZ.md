# A5 v3 — перенос интерфейса в существующий Directus

Дата: 19.10.2026. База проверки GitHub: `5cb9958181d4df211d9dcaccd16aa66439a8b8bb`.

## 0. Статус задания и обязательная граница

В пакете есть **работающий автономный интерфейс**, но нет зарегистрированного Vue-раздела, установленного bundle, live-проверки Directus или merge. Не объявлять весь A5 завершённым по наличию HTML. Приоритет: свежий `AGENTS.md`, актуальный код и ADR-002. Этот документ заменяет интерфейсные решения v1/v2, не отменяя серверные ограничения.

Дизайн v3 представлен владельцу как результат текущей итерации. Перед реальной интеграцией должно быть зафиксировано принятие именно этого визуального результата; не приписывать владельцу ещё не полученную оценку скриншотов.

## 1. Требуемое поведение

Менеджер просматривает текущие настройки без анкеты из 38 полей. Для короткой правки раскрывает нужную строку обзора. Для реквизитов, контактов, оформления и поисковых параметров переходит в основную область. Никаких одинаковых правых панелей для всех задач.

Пять внутренних направлений: «Обзор», «Компания», «Контакты», «Оформление», «Поиск и соцсети». Они представляют одну singleton-запись, а не пять разных записей. Служебные данные — свернутый readonly-блок.

Один draft-state на всю запись. Переключение групп и сворачивание краткой формы сохраняют ввод. Общий Save отправляет все dirty-разрешённые поля; интерфейс прямо говорит «Во всех разделах». Публикации, создания, удаления, списка и дополнительных singleton-маршрутов нет.

## 2. Разрешённый scope будущего исполнителя

Основные файлы:

- `directus/extensions/deere-shop-product-editor/src/sections/site_settings.js`
- `directus/extensions/deere-shop-product-editor/dist/sections/site_settings.js`
- `directus/extensions/deere-shop-product-editor/test/sections/site_settings.test.mjs`
- `docs/admin-sections/sections/site_settings/` — актуализированные документы и evidence.

Регистрация секции в `src/index.js` и `dist/index.js`, проверка singleton-маршрута и минимальная ссылка на раздел выполняются **одним lead-интегратором**, последовательно с другими задачами. Перед этим включить точные общие файлы в отдельный scope-lock. Не менять товары, категории, главную, страницы и статьи ради новой навигационной концепции.

Read-only: Directus schema/blueprints, роли и permissions, secret/configuration, Commerce API, storefront, Docker/deploy, профили сайтов, чужие данные и worktrees. Если для сохранения требуется новый серверный контракт — отдельная согласованная backend-задача, не скрытое расширение UI-diff.

## 3. Предстарт и технические блокеры

Получить свежий `origin/main`; новая изолированная ветка/worktree либо продолжение обнаруженной существующей A5-задачи. Не начинать повторную реализацию незавершённой ветки.

На **подтверждённой локальной Windows-инстанции** проверить:

1. `site_settings` действительно singleton, точный native response shape и способ проверки cardinality. Ноль, несколько записей или неподтверждённый результат блокируют запись. Одна видимая строка при фильтрующих permissions не доказывает глобальную единственность.
2. Metadata реальных полей: типы, required, readonly/hidden, native interface/options/conditions, relation file fields.
3. Эффективные read/update permissions текущего пользователя и item-level update. Неизвестные права — запрет записи. Administrator-only тесты не доказывают готовность ролей сотрудников.
4. `POST /commerce/mutations/site_settings/:id` и поддержка точного payload. Наличие коллекции в allowlist не доказывает серверный запрет чувствительных полей. Требуется принятый field-level контракт; при его отсутствии не обходить native PATCH и не включать «временно» незащищённый Save.
5. Native file picker для `logo`, `favicon`, `company_image`, `default_og_image`. Последние два поля имеют relation, но явный interface в старом snapshot отсутствует. Не заменять непроверенный интерфейс текстовым UUID-полем.

Схему, права и секреты ради прохождения предстарта не изменять.

## 4. Переиспользование A0

Обязательны действующие exports: `AdminShell`, `EditorToolbar`, `NativeFieldGroup`, `MediaPicker`, `ReadonlyDetails`, `createEditorState`; существующий механизм навигации и guards. Не создавать отдельный React/Next Admin. Не переносить макет через iframe и не подменять им штатный Directus.

`src/model.mjs` в этом архиве — только поведение offline-прототипа. **Не копировать его вместо A0.** Vue bridge должен обновлять reactive snapshot после начала и завершения async-операций, как предписывает контракт `createEditorState`.

У NativeFieldGroup — явный список полей и локальные русские подписи, полные initial values, контролируемое значение и effective permissions. Preserve native types/options/conditions/readonly. Глобальные metadata ради плотности формы не переписывать.

## 5. Поля и группировка

### Компания

Название: `company_name`, `legal_name`.

Реквизиты: `inn`, `kpp`, `ogrn`, `legal_address`, `vat_info`. Идентификаторы — текст, без числового преобразования и потери ведущих нулей. ИНН/КПП/ОГРН визуально короче адреса.

Раскрываемые ссылки: `requisites_url`, `documents_url`, с пометкой об отсутствии потребителя на текущей витрине.

### Контакты

Связь: `phone`, `email`.

Адрес/доставка: `address`, `city`, `working_hours`, `delivery_region`.

`messengers`: штатный повторитель по live metadata; при изменении label/url сохранять неизвестные свойства элементов. Неизвестный или неподтверждённый формат — readonly, не сброс к пустому массиву.

`social_links`: readonly до принятого контракта формата. Не показывать JSON-текстовое поле обычному менеджеру.

### Оформление

Файлы: `logo`, `favicon`, `company_image`.

Цвета и кнопка: `primary_color`, `accent_color`, `primary_cta_text`, `primary_cta_url`.

Подвал: `footer_text`, `footer_disclaimer`. Эти два поля имеют текущий потребитель; не маркировать их «неподключёнными» вместе с оформлением.

### Поиск и соцсети

`seo_title`, `seo_description`, `og_title`, `og_description`, `default_og_image`. Общая пометка: в проверенном main эти поля не подключены к глобальным метаданным витрины. Превью — только по запросу, с явной подписью «локальный пример». Не изображать фактическую выдачу поисковой системы.

### Защищённые поля

`commerce_profile`, `yandex_metrica_id`, `gtm_id`, `translations`, `id`, `created_at`, `updated_at` никогда не входят в `changes`. Профиль/конфигурацию не выводить сырым JSON: он может содержать чувствительные данные. `id`/`updated_at` используются для CAS в соответствии с правами.

Все отсутствующие на текущем экране значения сохраняются. Save не делает full-record replace, не очищает неизвестные JSON/отношения и не преобразует необработанные поля.

## 6. Сохранение и конкурентная работа

`expected` содержит исходные `id`, `updated_at` и исходные значения изменённых полей. `changes` содержит только dirty-поля из пересечения UI-contract, live metadata и действующих read/update permissions. Никакого client-admin token.

Одна запись — одна операция CAS. Нет публикации, автоматического создания записи или фонового пересохранения при открытии.

Успех подтверждается только валидным ответом с той же identity, наличием версии и всеми изменёнными полями; фактическое reread выполнить по принятому A0-контракту. Неполный/неопределённый ответ сохраняет ввод и блокирует повтор до reconcile.

При 409 показать сравнение «Мой вариант / Сохранено другим сотрудником». Выбор обновляет baseline после явного действия и не повторяет Save автоматически. Нельзя silently overwrite. Изменения других полей, сделанные сотрудником, сохраняются после rebase.

При потерянном ответе — «Проверить результат», а не «Повторить» без проверки. Если значения подтверждены чтением, показать подтверждение. Если отличаются — сверка.

При ошибке, достоверно возникшей до отправки запроса, доступен явный повтор. При 403/401 — состояние доступа, без обхода.

## 7. Файлы, доступность и влияние на сайт

Отвязка удаляет только relation, не файл. File permissions и публикационная eligibility проверяются отдельно. **Отсутствие визуального потребителя не означает отсутствия последствий для доступа к файлу:** связь с site_settings участвует в цепочке разрешения assets в gateway. Нельзя произвольно привязывать приватные клиентские вложения к публичным настройкам.

Ограничение 10 МБ и локальный выбор PNG/JPEG/WebP в HTML — ограничение демонстратора, не новая схема Directus. В реальной реализации действуют native file permissions, конфигурация и подтверждённые форматы.

Телефон, email, юридические сведения и тексты имеют точные потребители в отдельной матрице. Глобальные логотипы, цвета, CTA и SEO автоматически не подключать к Next.js в A5 UI. Учесть кеш; не обещать гарантированное появление ровно через 120 секунд.

## 8. Визуальные и поведенческие критерии

Desktop: компактные строки обзора, поля от 40 px, основной текст 14 px, подписи преимущественно 13 px, адекватные ширины по содержимому. Принятые Directus tokens и локальный scoped CSS. Без выдуманного логотипа, гигантского preview, KPI-карточек и английских рабочих подписей.

Mobile: одна колонка, поля не мельче 16 px, основные действия от 44 px, понятная внутренняя навигация. Панель Save не закрывает последние поля: safe-area, нижний отступ и поведение с клавиатурой проверяются на реальном устройстве. В малой высоте допустима незакреплённая панель.

Состояния: загрузка; readonly; ограниченные field permissions; нет доступа; нет/несколько записей; ошибка и повтор чтения; dirty; saving; успешное подтверждение; валидация; 409; uncertain; missing asset.

Внутри A5 переходы сохраняют ввод. Уход из раздела/закрытие страницы защищён. После сохранения и закрытия picker/dialog фокус возвращается в логичное место. Tab/Shift+Tab/Escape проверяются на реальных native компонентах. Модальное окно отмены не должно само терять ввод.

Контраст обычного информативного текста не ниже 4,5:1 в проверяемой светлой теме; отдельно проверить dark theme, если она поддерживается окружением. Автоматический контраст не доказывает все требования WCAG.

## 9. Порядок и приёмка

1. Зафиксировать принятую v3 и точный scope; preflight свежего main и локального runtime.
2. Проверить блокеры singleton, metadata, permissions, field-level CAS и file picker.
3. Реализовать controller/UI на A0, не переносить offline model/fixture.
4. Выполнить фокусные тесты поведения, включая конкурентную запись и ограниченные права.
5. Зарегистрировать секцию последовательно lead-интегратором; сверить src/dist.
6. Установить bundle в подтверждённый тестовый Directus; не выдавать browser module substitution за установку.
7. Реальные desktop/mobile снимки кандидата и сравнение с v3. Независимый code/visual review. Закрыть P0/P1/P2.
8. Выполнить `node scripts/verify-local.mjs` на точном кандидате. Mock gate не заменяет live checks.
9. Только после обязательных PASS commit/push/PR/merge; проверить итоговый main и очистить только собственную безопасную ветку/worktree.
10. Самостоятельный HANDOFF со статусом, SHA/PR, реальным runtime, тестами, review, cleanup и ограничениями.

Тестовые записи — только собственные синтетические fixtures с точным журналом ID и одним writer. Текущий singleton нельзя произвольно заменять демонстрационной записью из HTML. Не удалять по префиксу, не восстанавливать всю БД поверх чужой работы, не использовать глобальные prune/down -v.

Windows: постоянный checkout `D:\codex\Universal-Commerce-CMS-main`; Directus `127.0.0.1:18056`; проект `universal-commerce-cms-dev`. Существующий bind-mounted worktree не перемещать/удалять. Каждый target/mount/volume перед записью перепроверить. Production не входит в это задание.

# A1 category runtime acceptance

This opt-in Windows probe exercises the **installed** category candidate in the existing own Directus development runtime. It does not substitute candidate modules in a browser, restart services, change permissions/schema, edit another extension, change storefront source, or launch a storefront server.

From the repository root, after the lead confirms the candidate is installed at the mounted extension path and its artifact hash matches this worktree, run:

```powershell
node --env-file=dev/.env docs/admin-sections/sections/categories/runtime/a1-ux-runtime.mjs --synthetic-probe
```

The probe refuses non-Windows hosts, a different `DIRECTUS_URL`, any endpoint except `http://127.0.0.1:18056`, an unexpected Compose project/bind mount/volume, or category source/dist bytes that do not match the installed mount. It also verifies Directus serves the installed JavaScript registry bundle with the category editor and publication control present, recording only its SHA-256 rather than assuming the package identifier appears in that aggregate bundle. Directus and PostgreSQL may report different `dev/compose.yml` checkout paths; each checkout and the mounted extension are independently verified as this repository, and both services must share the named project network with `DB_HOST=db`. Full Windows paths and network identity stay in the private Temp journal; the public runtime summary records checkout names and the verified topology without absolute paths. It reads the existing `dev/.env` privately; credentials and authorization headers are never printed or written to evidence. `--only=<scenario-regex>` narrows browser scenarios while retaining runtime preflight, synthetic fixture setup, and exact cleanup.

The probe takes the shared `Global\UniversalCommerceCMS-Directus-runtime-acceptance` mutex. Every category and file UUID is reserved into a private Temp journal and durably flushed before its create/upload request. Native category create intentionally has no ID in the product payload; only this isolated Playwright transport injects the already-journaled ID so that a lost response still has an exact cleanup target. The installed application modules are never rewritten or intercepted. A narrowed `--only` run without `--site-effects` writes `results-closure.json`, preserving any full `results.json` report and clearly labeling its scope.

After login and again at the first mounted category list, the probe checks for delayed Directus onboarding overlays. It dismisses the observed “Have a license key?” prompt only when its license/core-plan choices and exact `Пропустить` button are present. It dismisses the observed “You have not set a project owner.” reminder only when the exact heading, visible `Почта владельца` label, MSCL compliance text, and exact `Remind Later`/`Set Owner` buttons are present; it clicks `Remind Later` only and never interacts with the owner field or compliance acceptance control. It does not select a license plan, accept terms, or change access settings. Human-copy checks are limited to the category list/editor and its own dialogs so native Directus branding does not count as category UI copy. If an unexpected native overlay blocks a scenario, that scenario records the original failure and later browser scenarios are skipped so exact cleanup can proceed without cascading timeouts.

For the lead-coordinated live storefront closure, the lead may run the same probe with `--site-effects` after the existing Next server is already running on `127.0.0.1:3000`. To run only the closure scenarios, use `--site-effects --only="native category card|status intent"`; this writes a separate `results-live-site.json` and preserves any full installed-probe `results.json`. A full installed probe with `--site-effects` writes both reports. The mode uses the existing non-admin technical gateway token supplied privately as `A1_STOREFRONT_GATEWAY_TOKEN`; it resolves the account ID from that credential, then uses the existing administrator session only for a read-only exact-account policy check. Every assigned direct or inherited policy must be explicitly readable and non-admin; the technical token is sent only from the Node process to Directus and is never exposed to the browser or evidence. It checks the published category API filter for all three publication states and inspects the live route response in memory for the owned category H1, introduction, SEO title and description. Raw response HTML and catalog data are not persisted. The category data fetch is cached for 300 seconds; the probe does not claim immediate storefront removal after a status change. This optional mode does not start Next or claim a site PASS unless it was explicitly run.

The bounded scenarios cover all retained server sort directions across two pages, comparing each rendered page with its real server response and checking stable ID tie-breaks; preserved search/status/filter/sort/page context; filter cancellation/focus and Apply; real category card/SEO readback and unknown SEO retention; explicit publication intent and ordinary-save status preservation; schema-gated unknown statuses; native draft creation and lost-ack retry blocking; validation/address errors and focus; actual guarded CAS conflict/reconciliation; lost, malformed, and readback-failed acknowledgements; anonymous denial and honest existing manager-role availability; native Directus file-library selection/unlink without deleting the file; and clearly separated no-results, controlled empty collection, injected permission failure, and injected network error states. The one-off probe records targeted desktop 1536×1024 and mobile 390×844 captures for list/card, validation, native create and uncertain create/update, conflict, and controlled permission/error states. Before unlinking the owned image, it stores the actual rendered image-field DOM and button metadata only in the private run directory, then requires one unique observed close icon control; it never deletes the file through the UI.

All raw journals, request traces, failures, DOM captures and screenshots stay under the run's private `%TEMP%/universal-cms-a1-ux-runtime/<run-id>/` directory. Cleanup queries only exact journaled IDs. Categories are deleted with the guarded mutation contract using a fresh full readable baseline and `action: "delete"`; the own PNG is deleted only after exact category reference checks show it is unused. Cleanup verifies collection-level absence. If cleanup cannot prove ownership or absence, the probe fails and preserves the journal/evidence for recovery; it never adopts a similarly named record or deletes by prefix.

Only after all selected scenarios finish without failure and every durably reserved fixture ID has verified exact-ID cleanup (including IDs whose create acknowledgement was lost) does the script write the corresponding sanitized report here. The summary omits credentials, request bodies, and fixture IDs. A skipped unknown-status scenario means the live schema rejected the synthetic status; it does not claim unknown-status runtime acceptance. Restricted-role acceptance is reported only when a pre-existing relevant role is visible and is not manufactured by this probe. No runtime PASS is claimed until the relevant report exists from the installed run; absent the opt-in site mode, live storefront effects are explicitly NOT RUN.

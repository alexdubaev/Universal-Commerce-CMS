## Визуальные образцы без повторного прикрепления архива

HTML — тот же одобренный интерактивный образец, не новая перерисовка. Вкладки: «Основное», «Первый экран», «Секции», «SEO», «Дополнительно». Дополнительные состояния доступны через `?tab=sections`, `?tab=seo`, `?tab=main`, `?state=conflict`, `?state=readonly`, `?state=empty`. Дополнительная группа поиска раскрывается в hero-вкладке.

Скопировать HTML и `check_reference.py` в собственный временный каталог вне Git. Проверщик создаёт восемь PNG и `reference-checks.json` рядом с собой, поэтому не запускать его поверх сохранённых исторических файлов репозитория. Он использует Python Playwright и Linux-путь `/usr/bin/chromium`; на другой ОС допустимо поправить только временную копию запуска под уже установленный Chromium. Не менять HTML ради прохождения проверки. При отсутствии Python Playwright можно отрисовать тот же HTML штатным браузерным инструментом проекта при 1536×1024 и 390×844, включая перечисленные состояния. Не менять зависимости приложения ради демонстрационного рендера.

Новый рендер может немного отличаться системным шрифтом; это не изменение утверждённой компоновки. Генерировать альтернативный дизайн не нужно. Подписи PNG в исходном VISUAL-ACCEPTANCE.md обозначают состояния, которые нужно получить из HTML. После реализации сравнивать их с настоящими скриншотами кандидата внутри Directus, а не выдавать эти PNG за runtime evidence.

`reference-checks.json` — историческая проверка только офлайн-макета (34 PASS), не новая проверка CMS и не production acceptance. При публикации материалов проверены целостность исходного ZIP, контрольные суммы копий и синтаксис проверщика/JavaScript. Общий `node scripts/verify-local.mjs` и runtime-приёмка A2 здесь не запускались. Материалы публикуются через draft PR; это не разрешение обходить локальный gate перед merge.

## Одна следующая задача

Реализовать только специализированный редактор существующей singleton-записи `home_page` по TASK.md. Переиспользовать актуальные A0, PageSectionEditor и утверждённые после A1-UI-FIX паттерны. Не переписывать CMS, категории или публичную витрину. Не начинать редактор «Страницы».

Родитель, дочерние секции и версии сохраняются раздельно. Не обещать изоляцию черновых правок существующей опубликованной записи: обычный CAS меняет текущую запись, и витрина может прочитать эти изменения. Слова «не публикует» означают отсутствие отдельного promote/смены статуса, а не гарантию невидимости правок. Отложенная публикация допустима только через доказанный version workflow. Не добавлять неподтверждённые кнопки, drag-and-drop или новые schema/API-поля. Защищённые области из TASK.md не расширяются этой публикацией.

## Как забрать материалы и начать

Ветка материалов: `docs/a2-home-approved-package`.
Каталог: `docs/admin-sections/sections/home_page/a2-approved/`.

1. Выполнить `git fetch origin` и создать собственные чистые временную ветку/worktree от актуального `origin/main` — не использовать ветку материалов как базу приложения.
2. Если этот каталог ещё отсутствует в main, в своём чистом worktree перенести только его:

```sh
git restore --source=origin/docs/a2-home-approved-package -- docs/admin-sections/sections/home_page/a2-approved/
```

3. Проверить опубликованные файлы по SHA256SUMS. Прочитать START-HERE → TASK → VISUAL-ACCEPTANCE → FIELD-CONSUMERS → действующие AGENTS/CONTRACTS и открыть HTML.
4. Реализовать одну задачу A2. Только после обязательных функциональных, runtime и визуальных проверок выполнить push, reviewed PR и merge. Приложить самодостаточный HANDOFF в одном копируемом блоке.
5. Если материалы остаются только в этой docs-ветке, сохранить их в проверенном implementation PR. Материальный PR можно закрыть как заменённый лишь после подтверждения сохранности файлов в main. Не удалять его ветку заранее.

## Правила, передаваемые дальше

Одна задача — один владелец реализации, новая временная ветка от свежего main; независимые read-only проверки допустимы параллельно. Автономные push/PR/review/merge разрешены только после зелёной функциональной и визуальной приёмки. Удалять лишь собственные объединённые ветки и чистые worktree. Чужую работу и данные сохранять. Deploy — только в подтверждённое собственное окружение с безопасным обновлением и откатом; неизвестный target означает DEPLOY BLOCKED, а не создание инфраструктуры.

Все ТЗ, промпты и финальные HANDOFF оформляются в копируемых блоках. В отчёте различать макет, проверочную загрузку в браузере, установленный bundle и production. После A2 остановиться.

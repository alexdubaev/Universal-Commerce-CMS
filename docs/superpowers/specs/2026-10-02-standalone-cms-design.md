# Universal Commerce CMS — выделение самостоятельной админки

Дата: 2 октября 2026. Статус: согласовано пользователем командой «Переноси»; самостоятельная база реализована и проверена; результат зафиксирован в [local acceptance](../../architecture/ACCEPTANCE-2026-10-02.md) и [implementation plan](../plans/2026-10-02-standalone-cms.md).

## Запрос и принятое решение

Создать самостоятельный проект в `D:\codex\Universal Commerce CMS`, чтобы использовать админку для других сайтов. Пользователь выбрал общую кодовую основу с отдельной CMS и базой для каждого сайта.

Для каждого сайта предусмотрены собственные Directus, PostgreSQL, файловое хранилище, пользователи, роли, секреты и настройки интеграций. Общая база нескольких сайтов и tenant isolation в эту работу не входят.

Основная единица повторного использования — версионированный код CMS и профиль сайта. Конкретные сайты подключают выбранную версию этого кода к своим экземплярам. Изменения общего ядра распространяются через проверенные версии, а не автоматически на работающие сайты.

## Исследовательская база

Актуальный источник: `D:\codex\deere-shop-worktrees\test-universal-cms`, ветка `test/universal-cms`, commit `4b241f0f6fb6c56002d18621af24cc10069c02f5`.

Папка назначения существует и на момент исследования была пустой. Исходный рабочий каталог имеет ранее созданные untracked-файлы тестов/Playwright; они сохраняются и не входят в перенос.

Подтверждённые факты:
- `directus/docker-compose.yml` уже запускает Directus и PostgreSQL без публичного Next.js сайта.
- `directus/schema/apply-schema.mjs` применяет не только коллекции и связи, но и `blueprint.seed`. Его нельзя запускать в новой CMS с исходными seed-данными без отделения профиля.
- Схема и Studio metadata содержат 14 основных и 9 вспомогательных коллекций.
- Принятый custom редактор товаров находится в `directus/extensions/deere-shop-product-editor`. Остальные разделы сейчас используют native формы Directus; ранее подготовленные макеты не являются реализованными новыми редакторами.
- `commerce-api` и `commerce-integrity` содержат необходимые редактору серверные контракты и hooks.
- Access blueprint содержит привязки к файловым папкам конкретного экземпляра.
- Revalidation installer требует URL и секрет публичного сайта; это интеграция конкретного сайта.
- Фактическая live-схема, права и установленный набор сторонних interfaces/plugins должны быть сверены при реализации. Статический blueprint не является выгрузкой БД.

## Подход

Рекомендуется новый независимый Git-репозиторий с административной частью и профилями сайтов.

Альтернатива — копия всего Deereshop с последующим удалением публичного сайта. Она переносит лишние зависимости и повышает риск смешивания общих компонентов с настройками магазина. Другой вариант — сохранить CMS внутри репозитория Deereshop как пакет; это не даёт запрошенной независимости проекта.

Новый проект имеет собственную историю, исходные файлы и версии. Это не дополнительное Git worktree репозитория Deereshop. В документе происхождения фиксируются исходный commit и извлечённые файлы.

## Что относится к общему ядру

- Directus и штатный Data Studio как основа админки.
- Согласованный редактор товаров: вкладки, native поля, file picker, dirty state, проверки сохранения и конфликта.
- Общие primitives будущих редакторов и единый стиль из подготовленного пакета макетов.
- Типовой commerce-профиль коллекций: настройки и страницы, каталог, статьи/FAQ, заявки/заказы и SEO-очередь — в пределах уже существующей модели.
- Установщики schema/Studio/access, принимающие выбранный профиль и настройки экземпляра.
- Нужные редактору guarded mutation/version API и integrity hooks с сохранением текущих контрактов.
- Тесты, документация запуска и сведения о происхождении.

Первый профиль — типовая commerce CMS на текущей модели. Не обещать произвольную отраслевую схему или генератор сайтов: новые схемы и виды сайтов могут добавляться отдельными профилями после проверки совместимости extensions.

## Что относится к профилю сайта

Название и оформление сайта, домен, контактные и юридические сведения, контент, категории/товары, настройки форм, публичные URL и revalidation callback, настройки уведомлений и разрешённые варианты каталога.

Статические шаблоны могут находиться в профиле. Реальные секреты, экземплярные UUID, база и файлы размещаются вне Git и не становятся частью общего профиля.

Профиль `commerce` содержит нейтральную демонстрационную конфигурацию. Все примеры синтетические; публикация контента по умолчанию не включается. Зависимые seed-записи и singleton-настройки должны удовлетворять required-полям и текущим integrity hooks.

Профиль Deereshop обозначает будущую отдельную адаптацию. Его наличие не подразумевает автоматический перенос или переключение действующего сайта.

## Что не переносится в первый baseline

- Публичный Next.js frontend.
- Реальная БД, uploads и содержимое каталога/заявок/заказов.
- `.env`, токены, пароли, резервные копии и настройки production/VPS.
- Runtime acceptance JSON, Playwright output и зависимости, установленные локально.
- Импорт подготовленного каталога Deereshop, его контентные миграции и editorial assets.
- SEO worker, importer и автоматически включённые уведомления/flows: они могут добавляться как отдельные согласованные модули.
- Брендовая тема Deereshop как обязательная тема платформы.

Необходимые штатные/сторонние interfaces, например SEO и редактор статей, сверяются по manifests и версиям. Извлечение не должно оставлять ссылки на отсутствующий interface или скрыто устанавливать другой plugin.

## Границы совместимости

На первом переносе сохраняются машинные имена коллекций и контракт `/commerce`, существующие product editor маршруты и совместимые interface identifiers. Косметическая смена названий и нейтральный branding не должны ломать связи Studio metadata с расширениями.

Путь extension package может сохранять историческое имя в первом baseline. Переименование package/interface ID требует отдельной явной таблицы соответствия и синхронных правок metadata; это не условие независимости Git-проекта.

Сторонние модули не получают новые права автоматически. Access installer настраивается только для нового экземпляра: идентификаторы пользователей, ролей и asset folders разрешаются внутри него, а не копируются из Deereshop.

Native API permissions сохраняются; токен администратора не встраивается в UI. Новые секреты создаются для нового экземпляра. Анонимный доступ не расширяется ради smoke.

Сохранить известные ограничения:
- Отсутствующие guarded contracts обозначаются как G1; перенос не включает их незаявленную реализацию.
- Аналоговые связи остаются только для просмотра до проверки identity-контракта G2.
- Parent save/version не означает атомарное или изолированное сохранение live `page_sections`.
- Условные snapshot поля не добавляются в форму при отсутствии их в фактической схеме.
- Managed child media не переводятся на другой формат автоматически.

## Изоляция первого локального экземпляра

Новый dev stack имеет отдельное Compose project name, собственные volumes и каталог uploads. Он не подключается к базе или файловому каталогу Deereshop.

Предлагаемый локальный Directus URL: `http://127.0.0.1:18056/admin`; порт подтвердить как свободный перед запуском. Публичный frontend не нужен для проверки админки. Revalidation/preview внешнего сайта остаются отключёнными до настройки соответствующего профиля.

Изменения нового `dev/compose.yml` и шаблона environment относятся только к новому проекту. Работающие контейнеры и конфигурация Deereshop не изменяются.

## Граница первого переноса

Разрешённая целевая область — новый проект `D:\codex\Universal Commerce CMS`. Исходный репозиторий читается; его файлы, БД, роли и окружение не меняются.

Первый baseline — самостоятельная административная часть с нейтральным commerce-профилем, проверенными server extensions, текущим custom редактором товаров и native экранами остальных коллекций.

Разработка остальных компактных редакторов начинается после этого baseline и переноса ранее подготовленных ТЗ в новый проект. В тех заданиях необходимо заменить исходные пути, базовый commit и зависимости A0; нельзя запускать их против нового проекта по старым allowlists без сверки.

Копирование исходников ограничивается tracked-файлами утверждённого набора. Для каждого переносимого файла фиксируются происхождение и исключённые настройки. Установка dependencies и создание/применение новой схемы выполняются только по scoped implementation plan.

## Проверка результата

Приёмка первого baseline требует:
1. Собственный Git-репозиторий и запускаемый dev stack без зависимости от пути Deereshop.
2. Чистый новый экземпляр с нейтральными данными и корректно установленными schema/Studio metadata.
3. Совместимые версии необходимых plugins и отсутствие неразрешённых interface references.
4. Проверки исходных schema/access контрактов и guarded mutations, адаптированные только в разрешённой области.
5. Свежий запуск 16 существующих product editor state tests и соответствующих серверных tests.
6. Native login и smoke списка/карточки товаров; сохранение синтетической записи, повторное чтение, media picker, сохранность ввода при конфликте/ошибке.
7. Проверка отсутствия старых контактов, каталожных данных, токенов, asset-folder UUID и абсолютных путей исходного проекта.
8. Desktop/mobile проверка UI и отдельное независимое ревью.
9. Подтверждение, что исходный repo/instances/volumes не изменились.
10. Документация создания нового экземпляра из выбранной версии и профиля.

Точные команды и разрешённые файлы перечисляются в implementation plan. Успешная проверка кода не заменяет фактический запуск новой CMS.

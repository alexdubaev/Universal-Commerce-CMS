## SKU/OEM semantics and fixture pitfalls

- Active `/commerce/search` normalizes to uppercase ASCII `A-Z0-9`, strips punctuation/whitespace, and validates normalized length 2..64. `SYN-504 836/ab` becomes `SYN504836AB`. Case and punctuation variants of a canonical article match the same prefix.
- Query uses `_starts_with` on `products.sku_normalized` or `products.mpn_normalized`, filters published products, and sorts by popularity then title. This is article lookup by prefix, not an equality-first ranking rule. A complete code can share its prefix with longer codes; an exact match is not explicitly promoted and can sit outside a saturated prefix window. Include that case in acceptance, but preserve D003 and the candidate ceiling. Titles and brands are not live search sources.
- The mock normalizer additionally retains Cyrillic and mock search includes title/brand substrings. Those successes are not live article-search evidence. Cyrillic-only input normalizes empty in the endpoint; mixed `АБ-12` becomes `12`. Do not manufacture native/non-ASCII article support from mock results.
- Product creation/update hooks derive normalized SKU/MPN and code fields from their source values. The identity rule is normalized brand plus ASCII article, not globally unique SKU across manufacturers. Use legitimate synthetic brand/SKU pairs, source SKU/MPN/code fields, and read back the derived values. Do not hand-fill derived fields or bypass guarded updates through SQL. Hooks do not prove legacy/imported rows were backfilled.
- Some comments/blueprint notes refer to `migrations/backfill-product-search.mjs`, but that file is absent from the current migration tree. Do not propose running it. Existing data normalization needs a separately scoped migration decision; hook-created synthetic data can exercise the present path.
- `dev/compose.yml:40` declares `COMMERCE_ENABLE_ADDITIONAL_CODES: "false"`. The handler skips `product_codes` entirely under that value; this was reproduced with the active handler offline. Canonical `products.mpn` still participates. An alias stored only in `product_codes` must currently return no code-only search match; rendering an alias on product detail does not imply it is searchable.
- Outside that declaration, the handler enables the optional source unless the value equals the exact string `false`. Collection absence or any codes-lookup failure degrades to normalized results. `meta.source=normalized` does not distinguish a deliberate disablement, empty code matches, or permissions/lookup failure. Capture warning counts and the effective flag separately when that feature is explicitly enabled later; no flag/config change is authorized here.
- Additional-code query limits rows before deduplicating products and has no explicit sort. Multiple active aliases or source/type variants for one product can consume its 200-row budget; inactive aliases and unpublished hydrated products are excluded. `source=codes` describes inclusion of code-derived products, not a full-catalog completeness promise.
- `candidateLimitReached` is computed in the pure merge but not emitted in endpoint response metadata. A total of 200 is therefore a bounded count, not proof that the catalog has exactly 200 prefix matches. Filter/sort results operate only within retained candidates; a filter does not expand that window to find omitted matches.

## Candidate filter, sort, and pagination cost

Unfiltered/unsorted live search makes one endpoint call and one product hydration call. It restores endpoint ID order after hydration. Filtering or an explicit sort first fetches the candidate set in 20-ID pages: one initial call, then up to nine concurrent additional endpoint calls, then one product query. Each endpoint page reruns the same underlying 200-product search; this is up to ten repeated searches to retrieve 200 IDs, not one DB query streamed into ten pages. When aliases are enabled, each endpoint call can also query code rows and hydrate code products.

Filtered results without explicit sort fetch at most 200 rows, restore candidate order, then slice in memory. Explicit sorts query/filter/count the retained IDs in Directus and paginate there. Existing tests verify that a 40-ID set is fully filtered/sorted before page two; they do not prove real Directus permissions, SQL query limits, or throughput. Both endpoint and catalog sort omit an explicit unique ID tie-breaker; stable repeated requests with tied popularity/title/price need data-based acceptance. Catalog changes between independent search page calls can also cause duplicates/misses; `Set` removes duplicate IDs but cannot recover missing candidates. First establish correctness on a static fixture set.

Revalidation is 15 seconds for search, 30 seconds for product lists, and 300 seconds for brands/categories/count/sitemap data. HTTP responses for sitemap also carry shared-cache freshness/stale windows. Record freshness and cache-hit state rather than combining warm storefront results with cold Directus measurements. Publication/price changes are not an immediate-consistency acceptance contract under these caches.

## Brands, counts, categories, indexes, and sitemap scale

- Brands use published-product `aggregate[count]=*`, grouped by raw brand, with a maximum of 500 rows. Counts are not surfaced as per-brand facets. Empty/blank labels are dropped; collisions collapse as above. More than 500 groups need a separately scoped enumeration policy. At 100k products, aggregation still needs actual plan/timing evidence; a response limit does not bound the database's input scan.
- Categories read published rows with limit 200, sorted by sort order/title. There is no product-count aggregation or cursor pagination. More than 200 categories can omit category routes/filters/static sitemap entries, and `getCategory` searches only this retained list. Include category cardinality in the real-data preflight rather than assuming 100k products implies fewer than 200 categories.
- Catalog count uses `filter_count` plus one `id` row. Missing count metadata falls back to that row count, which can turn a large product sitemap index into one chunk. The service identity must be able to return correct aggregate/count metadata; assert it against a known synthetic manifest, not only HTTP 200.
- Blueprint indexes cover status, category, availability, popularity, normalized fields and brand key; raw `brand` and `part_type` do not request indexes in the inspected product definition. Single-column indexes do not establish fast combinations or popularity/title/price sorts. Do not add speculative indexes now.
- Search SQL supplies ordinary B-trees plus `varchar_pattern_ops` indexes for prefix search under non-C collations. The pattern indexes are explicit migration SQL, not proof that the current DB installed them. `dev/apply-constraints.mjs` applies four SQL files, including these indexes, to the named local project with `ON_ERROR_STOP`; running it is schema mutation and outside this audit. It reads DB selectors from the ignored environment, so neither its env file nor credentials belong in report artifacts.
- Plan preflight should inspect index definitions, validity, column types, collation, normalized-null coverage, and actual equivalent SQL with `EXPLAIN` through the designated local DB only. A limit of 200 bounds returned candidates/memory, not scanned/sorted rows. Selective and broad prefixes can legitimately use different plans; do not require an index scan for every broad prefix.
- Product sitemap index uses chunks of 1,000 and count-based chunk enumeration. At exactly 100,000 included products this means 100 product sitemap files plus static sitemap. Chunk reads use stable ID ordering and offsets 0..99,000; they are bounded output queries, but late offsets and count execution still require measurement. Establish Directus and service-role effective limit >=1,000: silent truncation to 100 would skip most products while the next chunk advances by 1,000.
- Count and chunks are separate cached requests, not one database snapshot. Inserts/deletes/publication changes between them can duplicate or omit URLs under offset pagination. Verify the static fixture manifest for completeness, and test mutation/freshness behavior as a separate phase. Do not claim 100k readiness based on empty or small-fixture latency.

# Storefront ↔ Directus contract matrix

Scope: field and endpoint selectors currently used by the storefront adapters and API proxies. This is a source-derived integration contract, not evidence that a runtime instance grants these permissions or that live acceptance passed. It does not authorize schema, access, credential, or data changes.

## Read contract

“Required” below means required for the relevant storefront mapping/query to work, not necessarily `required: true` in the schema. Optional/nullable fields may be omitted or null. Unless stated otherwise, collection reads select only the listed fields and use bounded positive limits.

## Write contract

| Storefront route → Directus endpoint | Submitted fields | Canonical requirements and validation | Security and error assumptions |
| --- | --- | --- | --- |
| `POST /api/lead` → `POST /commerce/leads` | `{request_key,lead,attachments:[],attachment_manifest:[],action:"create"}`. Lead includes `name,phone,email,message,page_url,request_items`; optional company is prepended to message. Request key is validated/generated UUID. | Endpoint requires UUID request key; lead needs name (2–100 chars), absolute HTTP(S) `page_url`, and valid phone or email. Optional fields include `message,request_items,marketing_consent` and tracking/contact references in the endpoint schema. `request_items` max 100, each `{article,quantity}`. Route currently sends empty `attachments` and `attachment_manifest`; persisted status is server-set `new`. Parts-request rows require `site_settings.commerce_profile.features.parts_request=true`. | Extension requires authenticated accountability (`req.accountability.user`) and transaction-aware permissions; no anonymous/public write assumption. 400/409/422 are surfaced, other Directus errors become 502; generic local failure is 500. Idempotent retries must reuse the same key and equivalent payload. |
| `POST /api/order` → `POST /commerce/orders` | `{request_key,order,items}`; order is forwarded as supplied, items are forwarded. Route enforces 1–100 items and body ≤512 KB; key validated/generated UUID. | Endpoint requires UUID key and order fields `customer_name,phone,page_url,currency`; permits `email,comment,utm_source,utm_medium,utm_campaign,utm_content,utm_term,marketing_consent,marketing_consent_at,marketing_consent_version`. Each item requires `{product: UUID,quantity:integer 1..10000,unit_price:finite number}`. Profile must enable cart and currency must match; each product must be published, fixed-price, and current price/currency must match. Status and totals are server-derived; order and item rows commit atomically. | Extension requires authenticated accountability; caller identity is used for RBAC. No anonymous/public write assumption. 400/409/422 are surfaced; other failures become 502. Retry only with same key and payload. The current profile setting may keep this path disabled. |
| `GET /api/search` → catalog → `GET /commerce/search` and `GET /items/products` | Read only; query string `q`. Catalog may page and perform its post-search product read with the product selector above. | Search input 2–64 chars at proxy, normalized query 2+ alphanumeric at endpoint; candidate set capped at 200. | Authenticated/server-side Directus request uses the configured server token when present. Search endpoint uses request accountability or an explicit empty accountability object; it must never default to Directus admin bypass. |
| `GET /api/assets/[id]` → allowlist reads then `GET /assets/{id}` | Read only; asset UUID. Binary fetched only after a published-content reference check. | Allowed MIME types are images and PDF for inline response; other types become octet-stream attachment. | Server-side token only; no browser exposure of Directus token. | `GET /api/health` → `GET /server/health` | Read only; no fields. | N/A | Server-side health check; does not establish collection permission or storefront acceptance. |

## Field definitions and security assumptions

- Canonical application field definitions live in `directus/schema/blueprint.mjs`; shared content collections include `id,status,created_at,updated_at`. `created_at` and `updated_at` are Directus timestamp special fields. The storefront's stable product view keeps `date_updated` as its property name while querying CMS `updated_at`.
- Product required fields are `title,slug,sku,currency,price_status,availability_status`; catalog-facing text, price, brand, MPN, media references, category, JSON specifications, and SEO fields are nullable or optional. Do not infer permission requirements from optional schema fields.
- `site_settings` is a singleton; its `company_name,phone,email` are required. Home required selectors and child collection required fields are listed above. Content status defaults to draft, so public storefront reads explicitly constrain published data where applicable.
- Directus REST and custom commerce calls go through the server-only adapter. It adds `Authorization: Bearer <DIRECTUS_TOKEN>` only when configured. Correct operation therefore assumes a dedicated authenticated service identity with narrowly granted read access and write access only to the custom lead/order routes. Administrator is not an acceptable storefront identity. This report does not establish that the necessary role/policy is installed or supported on a given Directus edition.
- `STOREFRONT_ALLOW_MOCK_FALLBACK=true` permits specific caught read failures to become mock data. It does not change child-detail silent-empty behavior, navigation fallback behavior, asset-deny behavior, or helpers without catches. Mock-mode behavior is separately controlled by `STOREFRONT_MOCK_MODE` and Directus URL configuration. Do not interpret any fallback/mock success as a real CMS read.
- Existing Vitest `*-live.test.ts` files mock Directus requests. They can verify request selectors and mapping, but do not prove live field permissions, endpoint permissions, token accountability, real content, or end-to-end persistence.

## Acceptance interpretation

The contract can be used to construct explicitly synthetic, labeled local acceptance records and a least-privilege permission checklist. A selector returning empty data may be valid; a permission error must remain visible except where the code explicitly documents a fallback above. Write acceptance requires the API's accountability and profile gates, idempotent replay behavior, and atomic persistence. No runtime permission or content changes are authorized by this document.
